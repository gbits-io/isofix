Gbits · Comparative Review

Payment & Reconciliation Flows —
Korea vs. Switzerland

Two markets, two completely different answers to the same question: how does a payment become a booked entry in the accounting system? Korea solved it with real-time central APIs. Switzerland solved it with ISO 20022 files. That divergence decides where an ISO 20022 gateway creates value — and where it does not.

KR

Korean interactions — real-time APIs, no files

Domestic Korea runs on a centralised, real-time stack: mandatory e-Tax invoices to Hometax, and bank data pulled live from the KFTC Open Banking platform as JSON over REST. No XML statement files are exchanged. The friction sits entirely in the cross-border leg.

Invoice / tax Bank data Reconciliation Friction point Response

Hometax is non-negotiable

E-Tax invoices go to the National Tax Service in real time, and the returned approval number becomes the reconciliation key. Any foreign tool that can't speak to Hometax is locked out of the domestic loop.

One API covers every bank

KFTC Open Banking gives Douzone a single OAuth 2.0 REST interface across essentially all Korean banks, returning JSON on demand. There is no daily batch file to download.

Reconciliation is already solved

Matching happens against the Hometax approval number, in real time. An camt.053 file would be a downgrade in both latency and integration effort.

The gap is cross-border

Step ④ is the only slow, expensive, opaque hop in the whole diagram — and the only place where a stablecoin rail plus structured messaging changes the economics.

CH

Swiss interactions — ISO 20022 files, two rails, one format

Switzerland reconciles on files: the bank delivers camt.054 and camt.053 XML, and the ERP matches the QR reference carried in <CdtrRefInf>. Because the match key lives in the message, a Solana stablecoin payment can enter the exact same reconciliation path — that is the Gbits gateway.

Invoice Payment / ISO message Stablecoin / reconciliation Response

The match key travels in the message

Swiss reconciliation depends on the QR reference surviving the trip inside <CdtrRefInf><Ref>. Whatever produces that field correctly gets auto-matched — the ERP never asks where the money came from.

Why the Solana rail slots in

Steps ⑧–⑪ reproduce steps ③–⑦ exactly, but settle in seconds for a sub-cent fee. The gateway's only job is producing a file the ERP already trusts.

Batch latency is the fiat weakness

camt.053 arrives once a day. The Solana rail can emit a statement the moment finality is reached — the same format, fresher data.

CHF token is the open dependency

With VNX's VCHF discontinued, the CHF leg needs a successor. Safirum's CHF-S on Solana Token-2022 is the current candidate — pre-launch, and permissioned.

What the two diagrams say together

ISO 20022 is a Swiss-side product, not a Korean-side one

Put the diagrams side by side and the asymmetry is obvious. In the Swiss flow, the ERP is waiting for a file — so supplying that file is a product. In the Korean flow, the ERP is calling an API and already reconciling in real time against a Hometax approval number, so handing it XML solves nothing. Selling an camt.053 generator into domestic Korea would be pushing a batch format into a market that already skipped batch entirely.

The two diagrams touch at exactly one point: step ④ in Korea, the SWIFT cross-border hop. That leg is slow, expensive, and strips the structured invoice data the receiving European ERP needs. Replacing it with the Solana rail from the Swiss diagram — stablecoin settlement plus a generated ISO 20022 statement — fixes both halves at once: the Korean exporter gets funds in seconds, and the Swiss or EU counterparty gets the camt.053 its accountant demands.

So the Korean opportunity is not "sell ISO 20022 to Douzone users." It is own the corridor: be the layer that turns a Korean export payment into something a European accounting system books automatically. A Douzone- or ECOUNT-shaped JSON/REST connector — not an XML file — is what the Korean end of that corridor would actually consume.
